NarrativeMemory::load_or_init resynchronises one byte at a time

The previous commit left two possibilities open: `load_or_init` does real work
beyond the read, or the trace is wrong a fifth time. Reading the one function
the trace actually wrapped settles it, and it is neither -- it is a bug.

    if let Some(ep) = NarrativeEpisode::from_bytes(&data[pos..]) {
        pos += size;
        ...
    } else {
        pos += 1;
    }

The failure branch advances **one byte** and re-parses a whole episode from the
new offset. On the 25 KB test file that is up to 25,600 attempts, each running
`from_bytes` with its UTF-8 decoding, slicing and allocations -- per recall,
forever. That is the 8.45 ms: not 0.22 ms of I/O plus something, but a
linear resynchronisation scan that has almost nothing to do with reading a
file.

The resync exists to survive a corrupt or partial file. But `save` writes to
narrative_memory.bin.tmp and renames over the target, so a crash mid-write
leaves the previous complete file in place and the target is always either the
old good file or the new good file. The defensive scan is guarding against a
case the atomic rename already prevents -- and it is being paid for on every
single recall.

Two honest limits. Whether the scan actually fires today depends on whether
`from_bytes` succeeds at each `pos` the writer produced, which I have not
measured -- the reader recomputes `size` from the parsed episode while the
writer emits `to_bytes`, and any disagreement between those two layouts would
desynchronise the reader permanently and send it into the byte-at-a-time path.
That is the thing to confirm next, and a counter on the `pos += 1` branch
answers it in one run. And I have not changed anything: rewriting a parser's
recovery behaviour changes which episodes load, which is a correctness question
and not a latency one, and this commit is the diagnosis rather than the fix.

No code changed. 443 lib + 35 integration tests still pass.
