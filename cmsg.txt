Do not cache the state loads: the traced cost is not the file read

The previous commit concluded that the learning path is "whole-file loads, not
computation" and that three `fs::read`s cost 20.6 ms. Reading the code says
otherwise, and measuring outside the binary says otherwise harder.

NarrativeState::load_or_init is `fs::read` of a file whose own writer caps the
payload at 4,096 bytes, plus a fixed 21-float parse. EmotionalStateRing is
`path.exists()` and `fs::read`. Neither can take 6.45 ms.

Measured directly, outside the binary, warm:

  200 reads of narrative_memory.bin (25 KB)   43.2 ms total, 0.22 ms each
  200 reads of activations.bin    (152 KB)           0.20 ms each

So the 8.45 ms attributed to "narrative memory load" is roughly forty times
the cost of the read it is supposed to be made of, and the disk is not the
culprit either -- the free space on this volume has been the source of two
separate problems tonight and this is not a third.

That leaves two possibilities and this commit does not choose between them.
Either `load_or_init` does meaningful work beyond the read, or the trace
attribution is wrong a fifth time. The five wrong turns are worth listing:
activation density, result printing, the eight state saves, the gated sections
loads being unconditional, and now this. Four of them looked like a file-size
story and every one of them was something else.

What this does settle: **a cache is not the justified next step.** Caching a
0.22 ms read to recover 8.45 ms would be optimising a number that has not been
shown to exist. The same rule that ruled out the eight saves -- measure before
changing -- rules this out too, and it is the same rule that would have caught
each of the four earlier guesses.

No code changed. 443 lib + 35 integration tests still pass.
