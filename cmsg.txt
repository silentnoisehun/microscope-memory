Narrow the long-block embedding divergence to the provider's forward pass

Follow-up to c713e52 / 7d99c3d. Three measurements localise the defect.

1. It is not the stored index. A fresh build (probe_layers with three 865-920
   byte texts taken from the diverging evaluation index) produces vectors at
   cos 0.8568, 0.8052 and 0.8573 against the reference -- the same values the
   stored index gives. The index is faithfully storing what the provider
   returned.

2. It is not tokenization. MICROSCOPE_EMBED_DEBUG dumps the token ids the Rust
   provider produces; compared against the reference tokenizer for the same
   input, all three texts tokenise identically -- 128 ids, exact match. The
   reference pads to 128 with [PAD] and the provider trims to the real length,
   which is the same sequence.

3. So it is the forward pass or the pooling, and it is length-dependent: below
   ~300 bytes the provider reproduces the reference exactly (cosine 1.0000 over
   13,031 blocks), and above it degrades to ~0.77.

What is not yet established is which of the two it is. The obvious next test --
comparing the reference under different truncation and padding settings, and
computing the mean pool by hand from the final hidden state -- was started and
not finished, because the Python wrapper around the tokenizer returned a list
rather than an Encoding in three successive attempts and the attempt budget ran
out. Nothing was concluded from it.

The finding to carry forward is the narrowing: the defect is in the provider's
forward or pooling for long inputs, not in storage, not in parsing, and not in
tokenization. That is a real change in what is known, and it retires the two
earlier wrong explanations (1024-byte truncation, and the 512-token padding
fix, which addressed a different symptom).

No code change is included: nothing here is fixed, and the measurement is
recorded instead so the next attempt does not repeat it.
